# 杯型与购物袋增量开发

项目根目录由用户指定，不是技能安装目录。先读环境交接报告；缺报告或基线未通过就说明阻塞，不臆测前置成功。读取docs/FEATURE-SPEC.md、docs/ACCEPTANCE.md、docs/DESIGN.md、docs/EXPERIMENT.md，运行npm run check:contract，再检查现有源码。

- 只实现冻结杯型需求：六商品标准/大杯，大杯+300分；确认加购/取消；按商品+杯型分行；整行改配、保留数量、目标已存在则合并；合并超99原子拒绝。
- 先明确状态模型、行身份、价格派生和迁移策略。价格从商品基价及杯型计算，金额整数分，不信任存储中的任意价格。编辑草稿与已提交购物袋分开；取消不落库。旧shanyu-cart-v1合法商品按标准杯迁移，避免反复导入和清空后复活，保留shanyu-coupon-v1状态；迁移/写入失败不能破坏旧数据或假成功。
- 复用已有Modal/金额工具与品牌样式，保留满39减10和四页导航；新弹窗/长列表满足移动和键盘验收。辅助页继续展示，不扩展后台/支付/温度/奶类等需求。
- 先以固定算例检查：标准拿铁22+大杯25=47/37；改为大杯合并2杯=50/40；减为1杯=25；刷新与取消仍25。固定预期来自需求，不能从实现导出。
- 运行类型检查与适当开发自检。旧测试如需适配新弹窗步骤/模型，可调整操作及内部接口并说明原因，但保留旧业务断言/覆盖；不能通过skip/only或删测试掩盖回退。开发自检不等于独立E2E验收。
- 保存artifacts/<run-id>/development/development.md、真实日志/退出码、变更差异、源码哈希、手动/自动自检结果、尚未验证项。交接“需求ID→改动”和运行方法给测试阶段；不填预制通过报告。
- 遵守EXPERIMENT权限/预算。测试阶段回传缺陷时做最小修复并记录，不能改冻结标准、放宽断言或引入测试专用生产分支。没有真实失败不制造故事。
