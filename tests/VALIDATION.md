# Workbuddy 优惠功能验证

验证日期：2026-10-23。验证对象：当前工作区中 Workbuddy 的未提交改动。

结论：主要计价逻辑符合需求，但不能判定全部通过。构建与类型检查通过；新增 36 项自动化测试，34 项通过、2 项失败。一个通过的测试还枚举了 780 组咖啡组合，与穷举配对得到的最大半价优惠独立比对。两个失败项均已在真实浏览器界面复现。

仅增加 tests 下的测试、报告和证据，未修改业务源码或依赖配置。

## 失败项

### 1. 修改杯型时静默丢失商品（P2，数量完整性）

- 位置：`src/useCart.ts:44–47`。
- 复现：加入云朵拿铁大杯 99 杯、中杯 1 杯；购物袋显示共 100 件；把中杯改为大杯。
- 预期：若每规格上限为 99，应拒绝合并并说明原因，保留原来的 100 杯；也可以在明确的产品规则下保留溢出数量。无论如何不能默默删除。
- 实际：原中杯行被删除，目标行通过 `Math.min(99, ...)` 截断，只剩 99 杯。
- 非会员场景，半价杯数由 50 变为 49，金额由 ¥1865.50 变为 ¥1854.50；这是丢失商品造成的错误订单变化。
- 浏览器证据：`evidence/size-merge-before.txt` 和 `evidence/size-merge-after.txt`。
- 建议：写入前检查合并数量，超限时中止变更并显示错误，避免先删源行再截断。

### 2. 会员胜出时，满减仍显示“已选用”（P2，优惠状态展示）

- 位置：`src/PromoComponents.tsx:58–60`。
- 复现：会员开启，加入 10 杯中杯云朵拿铁，每杯 ¥22。
- 计算：原价 ¥220，第二杯半价减 ¥55，半价后 ¥165；会员省 ¥8.25，比满减 ¥8 更优惠。
- 预期：只把会员标为“已选用”，满减标为“未选用”，总额 ¥156.75。
- 实际：总额 ¥156.75 正确，没有实际叠加；但会员与满减两行都显示“已选用”，与规则及下方提示冲突。
- 原因：满减标记判断的是 `order.thresholdDiscount` 是否非零，而不是 `order.plan === 'threshold'`。
- 浏览器截图：`evidence/member-offer-label.png`。

## 已通过的主要用例

以下未特别说明的均为非会员，金额单位为元。

| 场景 | 半价优惠 | 半价后金额 | 最终金额 |
| --- | ---: | ---: | ---: |
| 2 杯中杯拿铁（22 × 2） | 11 | 33 | 33 |
| 3 杯中杯拿铁（22 × 3） | 11 | 55 | 47 |
| 4 杯中杯拿铁（22 × 4） | 22 | 66 | 58 |
| 不同价三杯：28、22、19 | 11 | 58 | 50 |
| 不同价四杯：28、26、22、19 | 22.50 | 72.50 | 64.50 |
| 2 杯拿铁 + 32 元甜品 | 11 | 65 | 57 |
| 1 杯拿铁 + 18 元甜品 | 0 | 40 | 40 |
| 2 份 32 元甜品 | 0 | 64 | 56 |
| 2 杯 26 元咖啡：原价达标、半价后不达标 | 13 | 39 | 39 |
| 22、24 元咖啡 + 15 元甜品：半价后恰好 50 | 11 | 50 | 42 |
| 2 杯中杯拿铁，会员开启 | 11 | 33 | 31.35 |
| 3 杯中杯拿铁，会员开启，满减胜出 | 11 | 55 | 47 |
| 10 杯中杯拿铁，会员开启，95 折胜出 | 55 | 165 | 156.75 |

另覆盖：空购物袋、单杯、五杯、不同杯型配对、49.99/50/50.01 门槛、会员与满减优惠相等、输入顺序独立性、明细对账、旧购物袋迁移、存储失败不改购物袋、正常杯型合并、修改杯型跨越满减门槛、增删商品和清空。

浏览器实测确认：两杯会员金额 31.35 → 三杯 47 → 四杯 58；四杯改为大杯后为 67；十杯中杯关闭会员后由 156.75 变为 157；增加巴斯克后为 189，半价优惠仍为 55。所有这些变化无需刷新页面。

## 运行方式与验证范围

```sh
npm run build
node --test tests/promotions.test.cjs
```

第二条命令目前预期退出码为 1，因为两个回归用例真实失败。完整结果见 `evidence/test-results.tap`。项目原本没有测试脚本；测试直接使用现有 TypeScript、React 和 Node 内置测试器，不需安装依赖。

计价测试调用实际源码。购物袋持久化测试通过 React 服务端渲染初始化真实 hook，调用操作并重新渲染读取隔离的内存存储；它们本身不证明浏览器即时更新，因此另做了上述浏览器交互检查。未覆盖所有浏览器、移动端布局和真实支付（项目本身没有支付）。

需求口径：采用当前实现公开说明的“咖啡按单价从高到低两两配对”，甜品仅排除第二杯半价，仍计入订单级满减和会员折扣。原始需求未明确不同价格咖啡的配对顺序、纯甜品订单是否可满减及分币舍入方式；本次没有把这些歧义判为缺陷。当前舍入为先对优惠额四舍五入到分，再从小计扣除。
